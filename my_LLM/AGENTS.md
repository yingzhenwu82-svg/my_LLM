# LLM Wild 中文研究知識庫 — AI 協作規範

> 本文件是本專案的最高層級開發與知識管理規範。任何 AI Agent（Codex、Claude Code、Cursor 等）在新增、修改或整理內容前，都必須先閱讀本文件。

## 1. 專案定位與目標

**專案名稱：** LLM Wild｜中文大型語言模型研究知識庫  
**專案目的：** 建立一個持續累積、互相連結、可追溯來源的中文 LLM 研究 Wiki。

本專案不是單純的文章收藏夾，也不是每次提問才重新檢索原始文件的問答系統。核心工作方式是：

1. 將論文、技術文章、官方文件等放入 `raw/`，保留原始來源。
2. AI 閱讀來源，整理重要概念、方法、實驗結果與限制。
3. 將整理結果整合進 `wiki/`，必要時新增或更新多個知識頁。
4. 更新索引 `index.md`、網站資料 `data/articles.js` 與異動紀錄 `log.md`。
5. 保留來源連結、日期與不確定性，讓知識可以被查證。

**核心原則：原始來源是證據，Wiki 是持續演進的知識整理，AI 是維護者，人類負責方向與審核。**

## 3. 知識分類與放置規則

| 類別 | 路徑 | 收錄內容 |
|---|---|---|
| 核心概念 | `wiki/concepts/` | LLM、Token、Embedding、Context Window 等 |
| 技術方法 | `wiki/methods/` | RAG、Fine-tuning、Prompting、Agent 等 |
| 論文導讀 | `wiki/papers/` | 論文摘要、方法、實驗、限制 |
| 應用案例 | `wiki/applications/` | 教育、醫療、程式開發等應用 |
| 研究問題 | `wiki/questions/` | 跨來源比較、爭議、研究假設 |

檔名使用小寫英文與連字號，例如 `retrieval-augmented-generation.md`。文章標題使用繁體中文，可在括號補上英文術語。

## 4. Wiki 文章格式

每篇 Wiki Markdown 文件必須採用以下格式：

```markdown
---
title: "文章標題"
category: "concepts"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
tags: ["LLM", "研究主題"]
sources:
  - "來源名稱或 URL"
---

# 文章標題

## 一句話摘要
用 1–2 句話說明核心概念。

## 為什麼重要
說明此概念在 LLM 研究或應用中的價值。

## 核心原理
以清楚的小節、流程或例子解釋。

## 優點與限制
避免只寫優點，也要整理適用條件與風險。

## 與其他概念的關聯
使用 Wiki 相對連結，例如：
- [[transformer]]
- [[retrieval-augmented-generation]]

## 參考來源
列出可查證的論文、官方文件或可靠文章。
```

若某個欄位不適用，需寫明「尚無資料」或省略並解釋，不可自行捏造。

## 5. 新增來源（Ingest）工作流程

當使用者提供新論文、文章、PDF 或網址時，依序執行：

1. **確認來源**：記錄標題、作者／機構、發布日期、網址與來源類型。
2. **閱讀原文**：優先讀取原始論文或官方文件；不可只依賴搜尋摘要。
3. **萃取資訊**：整理研究問題、方法、資料集、實驗結果、貢獻與限制。
4. **比對既有 Wiki**：先讀 `index.md`，再搜尋相關頁面，避免重複建立同義頁。
5. **整合知識**：新增或更新所有受影響頁面，補上雙向或必要的交叉連結。
6. **標示差異**：若新來源與舊內容不一致，新增「觀點差異／待確認」段落，不可靜默覆蓋。
7. **更新網站資料**：同步更新 `data/articles.js`，確保網站可以找到新增文章。
8. **更新索引與地圖**：更新 `index.md`、`sitemap.md`。
9. **追加紀錄**：在 `log.md` 最上方追加一筆 ingest 紀錄（保留舊紀錄）。
10. **回報人類**：列出新增／修改的檔案、重要發現、尚待確認事項。

一次來源可能影響多個 Wiki 頁面。不可只新增一篇摘要就結束。

## 6. 提問與研究（Query）工作流程

1. 先閱讀 `index.md` 與 `sitemap.md`。
2. 找出相關 Wiki 頁面並閱讀，不可只依賴單一摘要。
3. 若 Wiki 資訊不足，明確指出缺口；必要時請使用者補充來源或進行研究。
4. 回答時區分「來源明確指出」「跨來源綜合推論」「尚待驗證」。
5. 重要結論附上來源連結或 Wiki 頁面連結。
6. 若分析具有長期參考價值，詢問使用者是否要存成 `wiki/questions/` 的新頁面；使用者同意後再寫入。

## 7. Wiki 健檢（Lint）工作流程

定期檢查：

- 是否有沒有任何頁面連入的孤兒頁面。
- 是否有概念被多個頁面重複定義。
- 新來源是否推翻或補充舊結論。
- 是否有缺少來源、日期或限制說明的主張。
- `index.md`、`sitemap.md`、`data/articles.js` 是否與實際 Wiki 一致。
- 網站連結、分類篩選與搜尋是否正常。
- 是否有過期、失效或需要重新查證的來源。

Lint 只能提出有證據的修正；不可為了讓內容看起來完整而虛構資訊。

## 8. 網站開發規則

- 使用原生 HTML、CSS、JavaScript，維持 GitHub Pages 可直接部署。
- 不使用需要伺服器、資料庫、API Key 或建置流程的功能。
- 網站文章資料集中維護於 `data/articles.js`。
- `index.html` 負責頁面結構；`css/style.css` 負責視覺；`js/app.js` 負責互動。
- 新增文章時，必須同步新增 Markdown Wiki 頁與 `data/articles.js` 條目。
- 不可將整份文章硬寫進 HTML。
- 保持響應式設計，桌面與手機皆可閱讀。
- 搜尋至少支援標題、摘要、標籤與正文文字。
- 所有按鈕都必須有實際功能；不可留下裝飾性但無作用的控制項。
- 不可加入未經確認的個人資料、API Key、密碼或機密。

## 9. `data/articles.js` 資料格式

每篇文章需包含：

```javascript
{
  id: "unique-kebab-case-id",
  title: "繁體中文標題",
  category: "concepts | methods | papers | applications | questions",
  categoryLabel: "顯示用分類",
  summary: "約 40–80 字摘要",
  tags: ["標籤一", "標籤二"],
  readTime: "5 分鐘",
  updated: "YYYY-MM-DD",
  content: `<h2>文章內容</h2>...`,
  sources: [{ label: "來源名稱", url: "https://..." }]
}
```

`id` 必須唯一。網站內容以繁體中文撰寫，必要時保留英文術語。`content` 僅能放安全、可信的 HTML，不可插入 script 標籤或未經清理的使用者輸入。

## 10. 命名、連結與引用規則

- 檔名使用 kebab-case。
- Wiki 內部連結使用相對路徑或 Obsidian Wiki link，並確保目標存在。
- 外部來源需使用完整 URL。
- 引用論文時優先提供 DOI、arXiv 或出版社頁面。
- 不可捏造作者、論文名稱、年份、數據或實驗結果。
- 無法確認的資訊需標記「待查證」，不可寫成確定事實。

## 11. 修改前後檢查清單

每次修改完成後確認：

- [ ] 已遵守本文件與既有目錄結構。
- [ ] 新文章有來源、摘要、分類、標籤與日期。
- [ ] 相關頁面已補上交叉連結。
- [ ] `index.md` 與 `sitemap.md` 已同步。
- [ ] `data/articles.js` 已同步，網站能顯示新內容。
- [ ] 搜尋與分類篩選仍可正常使用。
- [ ] 沒有虛構資訊、失效的內部連結或洩漏機密。
- [ ] 已在 `log.md` 追加紀錄。

**最重要的規則：讓知識持續累積，而不是每次從零開始；讓每個重要結論都能追溯來源。**
